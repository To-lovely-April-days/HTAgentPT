## 设计顺序建议

与开发依赖顺序（表 12-1）对齐，设计按批次推进：

| 批次 | 界面 | 对应开发步骤 |
|---|---|---|
| 第 1 批 ✅ | **C2 全局框架 + A1 智能问答** | 步骤 3（第一个可给真实用户使用的版本） |
| 第 2 批 | C1、C4、E1、E2、E3、E8、E14、E17 | 步骤 1–2（权限骨架 + 语料入库链路） |
| 第 3 批 ✅ | E4、E19、E20 | 步骤 4（分块检视与重新解析） |
| 第 4 批 ✅ | A2、A3、E9 | 步骤 5（台账与意图路由） |
| 第 5 批 ✅ | B1–B8 | 步骤 6（故障案例） |
| 第 6 批 ✅ | D1、D2、E10 | 步骤 7（翻译） |
| 第 7 批 | E5、E6、E7、K1–K6 | 步骤 8（三级库与客户入口） |
| 第 8 批 | A4–A12、E11、E12、E13 | 步骤 9（文档生成，主功能） |
| 第 9 批 | H1–H4、E15、E16、E18、C3、C5、C6 | 步骤 10（回流、审核、运维） |

第 1 批先做，是因为 C2 全局框架一旦定下（导航结构、密级呈现方式、表格密度、来源标注样式、
色板与字号阶梯），后面 43 个界面都在继承它；A1 则是密级过滤、来源标注、阈值拦截三条核心规则
第一次在界面上落地的地方。

## 需要与需求方确认的两处文档歧义

1. **密级取值不一致。** 表 3-1 与 3-3 用「机密 / 内部 / 公开」，表 4-5 文档元数据「密级」字段
   却写「共享 / 私有 / 公开」，7.1 的 `knowledge_base.tier` 又是 `shared / private / public`。
   当前理解：**知识库分级**是共享库/私有库/公开库（物理分库），**文档密级**是机密/内部/公开
   （驱动角色可见性），两者是不同维度。原型按此理解绘制，需确认。

2. **管理员的问答权限。** 表 3-2 功能权限矩阵中管理员「检索问答」为「—」，3.2 与 3.4 又写
   「确需开通时须单独授权并记录」。原型按「默认关闭、可单独授权」处理，管理后台不出现问答入口。

3. **审核台归属。已于 2026-09 确认。** 表 9-1 把「审核台」列在管理后台下，但表 3-2 管理员列
   的「故障案例审核」是 —，审核权只有总部审核人有。按后者处理：审核台归 H 组（总部审核台），
   管理后台左栏为「后台首页 + 七个功能项」而非八项。又因 3.4 第一条「公司隔离为架构级约束」，
   审核人账号不存在于任何一家公司的部署里——H 组是同一份代码在**总部节点**以另一组配置
   渲染的结果，不是某家公司的部署里能切出审核人。

4. **管理后台导航在左栏，不在顶栏。** 表 9-1 管理后台八行、每项自带多级子功能，48px 顶栏
   放不下也无处挂二级。已按左栏 240 分三组（语料域 / 能力域 / 治理域）定稿，顶栏只留品牌、
   后台标识与用户菜单。售前售后仍为顶栏导航（各五项）。这是设计判断，非需求原文。

## 已确认的产品决策（2026-09）

| # | 决策 | 影响的界面 |
|---|---|---|
| 1 | 管理后台功能项七项，审核台归总部审核人变体 | E 组左栏、H 组 |
| 2 | 不做自助改密，用户菜单五项 | C2 用户菜单、E14（须加「重置口令」并进审计） |
| 3 | 管理员落地页为带告警条的后台首页 | 新增 E0 |
| 4 | 同账号多终端**互斥** | C1 登录拒绝态、C4 会话终止态，两者与令牌过期、账号停用都不同 |

决策 2 连带取消了原计划的「首次登录强制改密」页——用户无任何改密能力，该页无法成立。
净效果是管理员长期知悉全员口令，界面上补不了，只能以制度补偿。此处记录以免日后被当成
设计疏漏。
