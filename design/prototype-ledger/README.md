## 本批重点：字段级密级的两层裁剪

3.4 第五条要求合同金额单独标记为机密、按角色裁剪返回列；判定标准 M7 要求
「售后工程师检索台账可见项目但不见金额」。A3 切到售后时同时发生两件事：

**一、合同金额整行消失。** 不是打码，不是置灰，不是「***」。出现任何占位都等于确认
该字段存在且有值——对方只要知道"有这个数"就已经泄露了一半。

**二、机密文档整条不出现，且不报数量。** 同一项目对售前可见七份文档，对售后只出现五份；
界面上没有「另有 2 份不可见」这类计数。这与检索侧的规则同源：权限过滤在查询内完成，
应用层本就不知道被滤掉几条，任何计数既实现不了也泄露存在性。

裁剪也影响筛选器本身：A2 的「合同金额区间」筛选项对售后不渲染。只藏列不藏筛选，
等于留了一条用金额区间反推的通道。

## 结构化查询的空态与问答的空态不是一回事

A2 的无结果态刻意与 A1 的阈值拦截写法不同：

| | A1 问答 · 阈值拦截 | A2 台账 · 无结果 |
|---|---|---|
| 机制 | 重排分值低于阈值 | 字段精确匹配未命中 |
| 文案 | 未找到可作为依据的内容 | 没有符合条件的项目 |
| 附带 | 列出未达阈值的文档名供判断 | 回显当前条件，可逐条去掉 |
| 有无相关度 | 有，显示分值 | 无，不存在"可能相关" |

台账没有相关度概念，照抄问答的空态会凭空造出一个不存在的机制。

## E9 批量修正画的是它的真实用途

FR-3.6 的原文是「用于历史资料归集阶段的集中整理」。所以 E9 画的不是一个抽象的
批量编辑器，而是它实际要解决的那个问题：早期导入的台账里设备类型是自由文本，
出现「高压釜」「高压反应斧」「高压反应釜（防爆）」三种写法，都不在受控词表内。

词表外取值不参与筛选，也无法与文档元数据对齐——这正是归集阶段的主要工作量。
校验提示条常驻，批量修正模式下这些行自动选中，新值限受控词表取值。
