# 第 7 批上半 · K 组客户入口

对应开发依赖顺序步骤 8 的客户侧。**二期转微信小程序时承接的就是这一组。**

| 文件 | 内容 | 是否需登录 |
|---|---|---|
| `Main.dc.html` | K1 自助查询（搜索 + 常见问题） | 否 |
| `Result.dc.html` | K2 结果与自助排查步骤 | 否 |
| `Report.dc.html` | K4 提交报修（含提交成功态） | 否 |
| `Progress.dc.html` | K5 报修进度（凭单号 / 已登录） | 否 / 是 |
| `MyDevices.dc.html` | K3 我的设备 | 是 |
| `SignIn.dc.html` | K6 客户登录 | — |

## 登录不是前置门

上表前四项全部匿名可用。登录只是「我的设备」和完整工单列表的入口。

做成整站前置门会形成死循环：账号由售后在处理报修时开通（FR-7.4），**没账号就报不了修，
没报修就拿不到账号**。

配套的是 K4 的成功态——报修单号是页面主体元素，大号等宽字加一键复制。提交到开户之间
有一段空窗期，这个单号是客户唯一的凭据。不能用「请截图保存」代替，微信里下载也受限。

## 与内网是两套独立构建产物

不是一套代码加条件分支。共用会把内网路由表、角色名、内部接口路径打包进隔离区的资源
文件里——那是可以被直接读出来的信息泄露。

隔离区页面的所有链接只指向隔离区自身，不出现任何内网入口。

## 客户侧尺寸例外（对既定规范的公开例外，不是私自改规范）

内网那套是为桌面密集信息设计的，照搬到手机上不可用：

| 项 | 内网 | 客户侧 |
|---|---|---|
| 可点区域 | 控件高 24/26/28/32 | **最小 44×44** |
| 输入框字号 | 12.5 | **不低于 16**（低于 16 会触发 iOS 聚焦自动放大，页面随即错位） |
| 正文 | 14 | 15 |
| 主按钮 | 高 28 | 高 44 |
| 密级徽标 | h19 / 11px | 客户侧不展示密级 |

## 微信内核约束（现在就守住，二期才不用返工）

微信内核（Android 的 X5/XWeb、iOS 的 WKWebView）滞后于桌面「当前版本」：

- 不用 `:has()`、容器查询、`dvh`——新特性只做渐进增强
- 不用 `100vh` 定高，地址栏与键盘弹起会截断
- 不依赖 `window.open`
- 不提供文件下载（Word/PDF 在微信内受限）——恰好表 9-1 的客户入口功能里也没有下载项

## 用词边界

客户侧不出现：知识库、密级、私有库、共享库、工作台、管理员、审计、解析、分块、召回、
向量、阈值。K2 底部写「资料来源：CJF 系列使用说明书 第 5 章」，而不是「来自公开库」。

已加入构建期检查：`grep` 这些词，命中即不通过。

**未找到的文案不得暗示内容曾经存在。** 已撤回的内容对客户一律表现为未找到——写「该内容
已下架」等于向外部泄露了撤回行为本身。

## K5 给客户看的不是内部处理记录

售后的处理记录里有技术判断与备件信息（「确认为磁力耦合卡滞，非电气故障」「已带备件」），
原样透出既没用也不合适。客户侧只呈现两样：状态节点，以及工程师主动写给客户的留言。

这意味着工单需要区分**内部记录**与**对客留言**两个字段——B6 工单详情里那个「追加处理
记录」要拆成两处，或者加一个「同时发给客户」的勾选。这一点第 5 批没画到，记在这里。

## 一处命名调整

界面清单里 K6 原名「客户账号激活」。因已确认不做自助改密，客户账号同样由售后开通并告知
初始口令，不存在独立的激活流程——K6 实为客户登录页。清单已同步。
