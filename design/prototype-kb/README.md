## 同步里最容易做丢的一条

FR-2.2 的原文：「向量在本地按本机向量化模型重新生成；**同步包附带总部所用向量化模型的
版本标识，一致时可直接复用向量以省去重算**」。

把 E6 的开关切一下就能看出差别：

| | 版本一致 | 版本不一致 |
|---|---|---|
| 耗时 | 约 4 分钟 | 约 47 分钟 |
| 其中向量重算 | 0 | 约 43 分钟 |
| 检索影响 | 无 | 新增与更新的文档在向量生成完成前不参与检索 |

这个耗时差决定了管理员要不要把同步排在非工作时段。**不显示版本比对结果，他就无从判断。**

界面上只写版本标识（`emb-2025.06-1024d`），不写模型名——8.2 末段要求换引擎时不改业务代码，
界面同理。已加 grep 检查，本批无任何选型字样。

## 发布是复制，不是引用

FR-2.3：「发布即在公开库中创建该文档的**独立副本**并单独解析入库，原文档不变」。

副本编辑阶段左右并排，左侧标明只读。删段只作用于副本——这是发布前去掉内部分机、供应商
联系人、OA 流程号的地方。

代价也写在界面上：**之后修改原文档不会自动同步到已发布的副本**。不写这一句，运维会以为
改了原文对外就更新了，实际公开库里还是旧版。

## 撤回只删副本

FR-2.4：「撤回即删除公开库中的副本并立即停止对外可见，记录撤回原因」。

删的是公开库的副本，原库正本不受影响。所以**内网不存在「浏览时撞上已撤回」这个场景**——
内网用户访问的始终是正本，「已撤回」只是发布记录表里的一个状态。

对客户侧则一律表现为未找到，不提示「已下架」——那等于把撤回行为本身泄露出去。这一条与
第 7 批上半 K 组的文案规则是同一条。

## 密级是一次性选择

FR-2.1：「密级一经设定不可修改，需变更时新建库并迁移」。

新建库面板里用红色警示条写明了后果：库里每一份文档的可见范围都由它推导，改密级等于改动
全部历史文档的权限边界。同一个面板里「默认切分策略」则标注为随时可改——两者放在一起，
才看得出哪个是一次性的。

## 同步删除保留原文件

FR-2.6：总部已删除或撤回的文档，同步后在本地标记为已撤回并停止参与检索，**原文件保留至
下一次全量同步后清理**。

界面上写明了保留的理由：万一是误撤回还能恢复。只写「停止参与检索」而不说文件还在，
管理员会以为已经彻底没了。

## 新增两个校验脚本

`design/tools/check-holes.py` 这批做了补强——原来只查根键，漏掉了循环项字段。本批正好在
那个盲区出错：模板引用 `k.tierStyle`、`k.lockStyle`、`e.kindStyle`，`renderVals` 里从没
算过，画面上三处徽标会全部失去配色而毫无报错。补强后当场抓到。

`design/tools/check-js.py` 新增：把逻辑类抽出来做 `node --check`。这些类在打包时不会被
解析，语法错误要到画布里打开才暴露，且表现为整个 artboard 空白。

两个脚本已对已完成的八个目录全量跑过，均通过。
