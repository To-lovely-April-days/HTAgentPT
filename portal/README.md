# 客户门户（隔离区，独立构建产物）

K 组客户入口。**与内网 `web/` 是两套独立构建产物，不共享任何代码**——共用会把内网
路由表、角色名、内部接口路径打包进隔离区资源文件，那是可以被直接读出来的信息泄露。
二期转微信小程序时承接的就是这一组。

## 登录不是前置门

K1 自助查询、K2 结果、K4 报修、K5 凭单号查进度全部匿名可用。账号由售后在处理报修时
开通（FR-7.4）——做成前置门就成了「没账号报不了修、没报修拿不到账号」的死循环。
报修单号是提交到开户之间唯一的凭据，成功态把它做成页面主体（大号等宽 + 一键复制）。

## 移动优先（对内网规范的公开例外）

可点区域最小 44×44；输入框字号不低于 16（低于 16 触发 iOS 聚焦自动放大）；正文 15；
不展示密级。微信内核约束：不用 `:has()`/容器查询/`dvh`，不用 `100vh` 定高。

## 用词边界（构建期强制）

客户侧不出现内部概念词。`pnpm build` 末尾运行 `check-words.mjs` 扫描构建产物，
命中即构建失败。已撤回内容对客户一律表现为未找到——不写「已下架」。

## 服务端匿名端点

- `POST /api/portal/search` — 仅公开库、仅关键词路径（不把嵌入服务暴露给未鉴权流量）
- `POST /api/portal/tickets` — 匿名报修；设备编号选填，对上台账则挂到对应客户名下
- `GET /api/portal/tickets/{no}?contact=` — 单号 + 提交时联系方式同时匹配才返回（防枚举）；
  只返回状态节点与对客留言，内部处理记录不透出

登录后走 `/api/auth/login` 与 `/api/customer/*`（K3 我的设备、全部报修）。

## 运行

```bash
pnpm install
pnpm dev        # http://127.0.0.1:5174，/api 代理到 127.0.0.1:5210
pnpm build      # tsc + vite + 用词边界检查
```
